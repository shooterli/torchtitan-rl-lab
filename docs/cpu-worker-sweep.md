# 缓冲深度与生成并发的对照

[手册目录](index.md) · [基础实验与假设](cpu-scheduling.md)

上一组 CPU 模拟保持两个生成 worker，缓冲加深后吞吐提高。继续把 worker 数设为 1、2、4，可以观察其中多少收益需要额外的生成并发。本次仍使用 24 个 group，普通生成耗时 2 秒，group 0 耗时 12 秒，每步训练 1 秒，采用就绪优先策略。权重更新即时可见，槽位在训练完成后释放。

## 复算九组实验

在项目根目录运行以下命令。每次调用输出 target 为 0、1、3 的结果。

```bash
python3 simulate_scheduling.py --workers 1
python3 simulate_scheduling.py --workers 2
python3 simulate_scheduling.py --workers 4
```

## 一个 worker 已能显示计算重叠的作用

串行基线需要的总时间为 `24 × (2 + 1) + (12 − 2) = 82` 秒。一个生成 worker、两个槽位时，它在训练器消费上一组的同时生成下一组。全部生成工作需要 `24 × 2 + 10 = 58` 秒，最后一个训练步再用 1 秒，所以在这个案例里总时间为 59 秒。继续增加到四个槽位仍是 59 秒，因为这条单 worker 生成时间线已经连续工作。

## 槽位也限制能同时工作的生成器

target 为 0 时只有一个槽位，生成完成后仍占用槽位直到训练完成，因此四个 worker 中也最多只有一个同时生成。target 为 1 时，四个 worker 与两个 worker 同样受到两个活跃槽位限制，两者均用 42 秒。target 为 3 时有四个槽位，四个 worker 可以同时工作，总时间降到 26 秒。

26 秒也达到这个案例的训练下界。训练器最早在第 2 秒收到一个普通 group，随后必须完成 24 个单秒更新，因此总历时至少为 26 秒。达到这个下界时，最早启动的慢 group 用版本 0 生成，在被消费前已有十次更新，最大年龄达到 10。这组配置应同时报告吞吐和年龄。

## 回到真实 TitanRL 时核对什么

TitanRL v0.4.0 按活跃槽位数启动 rollout worker，并从 rollout 规模推导生成器的 `max_num_seqs`。两者和生成器 GPU 数、TP/DP 布局是不同参数。做真实实验时，记录 GPU 布局、并发请求上限和实际运行中的请求量，才能判断吞吐提升来自减少训练等待还是增加有效生成并发。 [控制器的 worker 启动与并发推导](https://github.com/pytorch/torchtitan/blob/v0.4.0/torchtitan/rl/controller/controller.py) · [固定生成上限的对照](throughput.md)

本页结果来自已执行的确定性模拟，测试覆盖 1、2、4 个 worker 的资源上限和时间记账。下一步在相同资源配置下加入非零权重同步时间，观察生成器版本更新和槽位释放延迟。

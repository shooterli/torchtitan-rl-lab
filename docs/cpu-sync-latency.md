# CPU 实验中的权重同步延迟

[手册目录](index.md) · [基础实验](cpu-scheduling.md) · [固定生成资源的对照](cpu-worker-sweep.md)

前两组 CPU 实验假设参数更新后，生成器立即看到新权重。现在加入 `--sync-time`，用一个阻塞同步基线观察权重发布和槽位释放的延迟。生成时长、两个生成 worker、24 个 group 和单步一秒训练都沿用基础实验。

## 权重何时可见

训练在 `train_end` 完成，训练器策略版本加 1。经过指定同步时间后到达 `sync_end`，生成器版本才更新，当前 group 的活跃槽位才释放，训练器才可以开始下一个训练步。已在生成中的 group 保持采样版本，其他已有槽位里的工作可以继续用生成器当时可见的版本开始生成。

这个模型把每次同步设为完整阻塞阶段，包含最后一次更新后的同步。真实 TitanRL 会把同步的部分阶段与计算重叠，具体顺序还随版本变化。这里用独立参数明确时间与版本边界，后续可据此增加重叠模型。 [v0.4.0 槽位释放逻辑](https://github.com/pytorch/torchtitan/blob/v0.4.0/torchtitan/rl/controller/controller.py#L1272-L1292) · [后续 push 时序调整](https://github.com/pytorch/torchtitan/pull/5235)

```bash
python3 simulate_scheduling.py --sync-time 0
python3 simulate_scheduling.py --sync-time 1
python3 simulate_scheduling.py --sync-time 3
python3 -m unittest test_simulate_scheduling -v
```

## 用时间记账检查最后一次同步

target 为 0 时，每个 group 完成生成、训练、同步后才能开始下一个。24 个 group 的总时间为 `24 × (2 + 1 + sync_time) + (12 − 2)`。当同步为 3 秒时得到 154 秒，与程序一致。

`batch_wait` 从前一个训练步结束算到当前训练开始，因此包含前一次同步造成的间隔。最后一次同步发生在全部训练完成之后，需要单独计入。汇总满足 `总时间 = batch_wait 总和 + 总训练时间 + final_sync_seconds`。加上 `--json` 可以同时查看 `train_end` 和 `sync_end`，核对采样版本是否已发布。

例如三个等时 group、一个 worker、四个槽位、同步 3 秒时，group 0 在第 3 秒完成训练，但新版本要到第 6 秒才对生成器可见。group 2 在第 4 秒开始生成，仍记录版本 0。测试专门覆盖这个区间，避免把训练完成误当成生成器加载完成。

零同步参数保留了之前两份 CSV 的统计结果。扩展测试覆盖 243 组资源、窗口与同步参数组合，并检查任务完整消费、worker 和活跃槽位上限、训练互斥、采样版本、同步时间及收尾记账。所有秒数和吞吐来自 CPU 离散事件模拟。GPU 性能与实际权重同步延迟待测量。
